# 技能封装与接入 v0.9

当前优先把我们自己可使用、可迭代的版本做好，完整代码放在同一仓库持续更新。用户上传资料、通过对话补充意图、查看并修改实际成果；内部模块负责记录依据、影响范围和版本。当前交付是 Skill、独立核心模块和本地工作台；后续才考虑 Panda 既有客户端及线上端，正式部署接口不是本轮前提。

## 已有实现与剩余连接

| 层 | 本轮实际实现 | 当前边界 |
| --- | --- | --- |
| 专业工作流 | panda-content-layout v0.9；案例推演、渐进对话、跨媒介表达、分层反馈 | 由具备读图/文件工具的代理执行，不是自动 NLP 引擎 |
| 内容状态 | content-workflow：来源、事实/观察/解释/建议、决策、内容单元、输出映射、复核、历史 | 校验结构和依赖，无法证明来源真实或推理正确 |
| 风格记录 | style-profile：具体规则、候选/试排/认可/否定、素材适配与原资产保护 | 不能通过规则判断高级感，仍须真实样页和反馈 |
| 本地服务 | GET/PUT workflow、持久化、双版本检查、项目资产引用检查、导出失效 | 旧界面没有对话入口；旧 planner/renderer 不消费 workflow 或 style-profile |
| 制作与导出 | 既有 PPTX / HTML / PNG 试制链与 v0.8 已渲染样稿封装 | 此次未将旧排版升级为新审美，也未重新验收住宅成品 |
| 后续 Panda 接入 | 保留稳定数据边界、模块入口和测试 | 本轮暂不处理正式部署，不指定客户端语言/框架 |

## 接入顺序

1. 宿主沿用已有上传、会话、项目与模型网关。每次用户上传先保存原件，再由实际读图/文档工具读取，记录范围。解析成功与语义阅读分开。
2. 代理按 Skill 理解当前目标，将提取结果作为显式操作提交给 content-workflow。用户不填内部 JSON，年龄与性别不直接推断生活习惯。需要纠正事实时保留新的用户证据。
3. 把内容单元交给作者适配器。作者适配器选择真实模板或风格候选，保存素材位置和引用，调用实际可用的 PPT/网页/图片制作工具。模型供应商 ID 与能力从宿主配置取得。
4. 实际渲染，再分别记录内容、视觉、编辑性与兼容性检查。风格适配通过只能进入试排，不代表审美通过。收到用户具体反馈后才保存认可范围。
5. 改稿由依赖图列出影响的内容与媒介。只重做受影响部分，旧产物标明版本。每个目标产物重新通过其检查后再交付。

第 3 步作者适配器和正式宿主模型适配是下一段实现，当前不能拿旧 `/plan` 的规则初排冒充它们。

## 模块入口

Node.js 22+，核心模块没有外部依赖：

```js
import {
  createContentWorkflow, applyContentWorkflow, inspectContentWorkflow,
  createStyleProfile, recordStyleFeedback, inspectStyleFit,
} from './src/core/index.mjs';

let workflow = createContentWorkflow();
workflow = applyContentWorkflow(workflow, {
  type: 'setBrief',
  value: { mode: 'existing', audience: '业主', purpose: '理解已有方案对日常生活的回应', outputs: ['ppt'] },
}, { expectedRevision: 0 });
console.log(inspectContentWorkflow(workflow));
// 此时没有内容与图证，readyForProduction 为 false。
```

具体合同：[内容状态](content-workflow-contract.md)、[风格记录](style-profile-contract.md)。`readyForProduction` 只表示结构可以交给制作规划，不是成品通过或用户认可。`inspectStyleFit` 只返回候选适配结果；真实性和审美由外部执行记录与实际用户反馈负责。

## 本地 HTTP 适配

先启动既有本地服务并从 `/api/session` 取得当前会话 token。服务只监听 127.0.0.1；写入使用原有 `x-panda-token` 和同源保护。

`GET /api/projects/:id/workflow` 返回 `projectRevision`、`workflow` 和 `inspection`。旧项目没有 workflow 时产生未写盘的初态，已上传的文件登记为 unread，已有输入可作为待完善 brief，不猜任务模式与输出目标。

`PUT /api/projects/:id/workflow` 请求：

```json
{
  "expectedRevision": 0,
  "expectedWorkflowRevision": 0,
  "change": {
    "type": "setBrief",
    "value": { "mode": "existing", "outputs": ["ppt"] }
  }
}
```

两个 revision 必须来自最新 GET，示例中的 0 不可写死。成功后项目和 workflow 升版、旧导出失效；原 slides 保留。错误批次原子回滚，版本冲突返回 409，无效结构返回 400。workflow 中的资产 ID 必须来自当前项目上传，不能引用另一个项目的文件。

会话能力继续声明 `modelConnected:false`。接口同时区分 `legacyPlannerConsumesWorkflow:false` 与 `legacyRendererConsumesWorkflow:false`；`integration.legacyInputsDifferFromWorkflow` 显示旧 brief/audience 与新记录的差异，`integration.legacyAssetRolesDifferFromWorkflow` 显示旧资料分类和新语义角色不一致的资产。由适配器理解处理，不能悄悄覆盖用户确认的意图。

本地工作台的“内容底稿”视图读取这些记录，供当前助手和使用者核对。它不要求用户填写机器字段，也不增加一个未接模型的假聊天框。这里的对话完成理解、写入底稿后，在工作台刷新即可查看。反馈记录目前没有独立 resolved 状态；调用方须保留后续处理记录，不能把结构就绪当作反馈全部解决。

## 怎样测试、怎样才可交给普通用户

```text
node --test test/content-workflow.test.mjs test/style-profile.test.mjs test/server-workflow.test.mjs test/server.test.mjs test/production-manifest.test.mjs
node scripts/verify-resources.mjs
```

核心测试覆盖原子更新、证据角色、局部读取、跨媒介改稿依赖、风格版本和拒稿状态。HTTP 集成测试启动真实临时本地服务，使用隔离项目检查读写、并发冲突、重启恢复；注入可控导入/渲染替身，不等于真实文件导出或客户端端到端验收。完整旧渲染测试另需工作台依赖，见[运行方式](本地工作台.md)。

发布给普通用户之前必须补齐以下实测：正式 Panda 从上传到对话、样页、改稿、下载的整条路径；只给图片、混合文档与图纸、固定模板与 Logo 等真实任务；目标 PowerPoint 的实际编辑、网页桌面与手机阅读、图片输出清晰度；断线/失败恢复与旧版本保护；未经讲解的新使用者能完成任务。记录具体任务及文件，不能用一份自动测试总数代替。

风格至少以当前目标的真实内容检验，用户认可范围要明确。此前被否定的住宅样稿继续留作失败样本，不进入成功风格库。未完成正式宿主、作者适配和视觉验收前，版本定位为开发接入候选，不称可商用成品。
